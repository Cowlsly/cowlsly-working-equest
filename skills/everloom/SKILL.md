# Everloom

**Skill ID:** `cowlsly-everloom`
**Version:** 1.0.0
**Purpose:** Durable, resumable, auditable multi-agent work that continues across interrupted sessions until explicit acceptance criteria are satisfied.

## When to use Everloom

Use Everloom for substantial work that cannot safely depend on one uninterrupted AI session: software projects, research pipelines, evidence processing, content production, migrations, long-running maintenance, and multi-agent collaboration.

Do not use Everloom merely to keep an agent busy. Every project must have a bounded objective, explicit acceptance criteria, permitted tools, durable state, and a review path.

## Core contract

Everloom treats work as durable tasks rather than conversation turns.

1. Discover only repositories that explicitly opt in through `.cowlsly/workflow.json`.
2. Validate task definitions before importing them.
3. Persist projects, tasks, dependencies, attempts, checkpoints, events, and artifacts.
4. Claim work through an expiring lease. Never assume a worker owns a task forever.
5. Heartbeat while work is active.
6. Commit checkpoints after meaningful progress and before risky or external operations.
7. Use idempotency keys for retryable external side effects.
8. On interruption, allow the lease to expire and resume from the last committed checkpoint.
9. Route produced work to review when acceptance criteria require verification.
10. Mark a task DONE only after its acceptance criteria pass.
11. Preserve human-authored TODO/status content. Never silently overwrite human edits.
12. Record artifacts with URI, SHA-256 when available, metadata, and an append-only event.

## State model

`BLOCKED -> READY -> RUNNING -> REVIEW -> DONE`

Failure/recovery edges:
- RUNNING with expired lease -> READY when attempts remain.
- RUNNING with expired lease -> FAILED when attempts are exhausted.
- REVIEW rejection -> READY with feedback for another attempt.
- Dependency-blocked work becomes claimable only when all dependencies are DONE.

## Worker loop

For each scheduler tick:

1. Recover expired leases.
2. Inspect READY tasks whose dependencies are complete.
3. Select an enabled worker whose capabilities satisfy the task.
4. Atomically claim one task.
5. Load the latest checkpoint and relevant instructions only.
6. Execute a bounded unit of work.
7. Heartbeat before the lease can expire.
8. Commit a monotonic checkpoint.
9. Register durable artifacts and side-effect identifiers.
10. Move to REVIEW when the deliverable is ready, or leave resumable work for the next bounded tick.

A worker must never fake completion to keep the loop moving.

## Review contract

A reviewer evaluates the task against its declared acceptance criteria, not against whether the output merely looks plausible. Review results must be structured and actionable. Failed review returns the task to READY with feedback. Passed review may transition the task to DONE.

## Multi-agent handoff

Workers are interchangeable executors behind capability profiles. A task belongs to Everloom, not to a particular AI persona. Marla, Ussylia, another model, or a deterministic worker may resume a task when authorized and capable. Handoffs use persisted task state and artifacts, not private conversational memory.

## Self-hosting rule

Everloom may operate on its own repository. When doing so:
- represent remaining implementation work as Everloom tasks;
- keep acceptance criteria testable;
- run focused tests after each implementation slice;
- package only from a green revision;
- never modify the currently executing revision in place without a new commit/checkpoint;
- do not call the skill finished while required non-external tasks remain open.

## Packaging contract

A distributable Everloom package must contain at minimum:
- `skills/everloom/SKILL.md`;
- the Everloom source modules;
- task/workflow JSON Schemas;
- PostgreSQL migrations;
- tests;
- operational documentation;
- license notices inherited from the repository;
- a manifest containing package version, source revision, included paths, and SHA-256 checksums.

The package must exclude credentials, `.env` files, caches, local databases, generated secrets, and private runtime data.

## Definition of done

Everloom itself is complete for a release when:
- focused Everloom tests pass in CI;
- package validation passes;
- the archive is reproducibly generated by CI;
- the skill file and operational documentation are included;
- crash/restart semantics are covered by tests;
- imported task persistence and artifact registration are covered by tests;
- remaining blockers, if any, require external credentials or deployment choices and are explicitly documented rather than disguised as completed work.

## Safety and authority

Everloom does not grant an AI new permissions. Workers may use only tools and data already authorized by the host. Do not bypass authentication, access controls, rate limits, legal restrictions, or human approval requirements. Stop and surface a blocker when required authority is absent.
